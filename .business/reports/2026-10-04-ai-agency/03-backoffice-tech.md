## 0. 판정: 조건부 가능

**기술적으로는 쉽다. 막히는 지점은 채널 정책과 운영 규율이다.**

| 구분 | 판정 | 이유 |
|---|---|---|
| 쿠팡·카페24·아임웹·11번가 연동 | 가능 | 판매자가 키를 발급하고 대행사 서버 IP를 등록하면 끝난다. 쿠팡은 "자체개발(직접입력)"에 대행사 IP를 넣는 방식을 공식 안내한다 |
| **네이버 스마트스토어 직접 API** | **현재 사업자 형태로는 어려움** | 네이버는 외부 업체가 판매자의 "내스토어 애플리케이션" 키를 받아 서비스를 운영하는 것을 금지한다. 정식 경로인 "API대행사"는 **국내 법인 사업자**가 아니면 반려될 수 있다(2026-04 공식 답변). 창업자는 개인사업자다 |
| G마켓·옥션(ESM), 카카오 선물하기 | 조건부 | 둘 다 셀링툴 업체·연동대행사로 등록하고 승인받아야 한다. 승인은 플랫폼 재량이다 |
| 재고 "양방향" 동기화(채널에 재고 수량 쓰기) | 초기에는 비추천 | 기술적으로는 되지만, 버그 하나가 품절 상품 판매(오버셀)로 이어지고 그 손해를 대행사가 떠안는다. 사방넷·플레이오토가 이미 하는 기능이다 |
| 주문 취합·정산 대사·손익 리포트(읽기 전용) | 가능 | 핵심 가치이면서 위험이 낮다 |
| 1인이 15곳 운영 | 조건부 | 표준화된 커넥터, 모니터링, 키 만료 자동 알림이 있어야 한다. 이 셋이 없으면 8~10곳이 상한이다 |

**성립 조건 4가지**
1. **네이버는 3가지 경로 중 하나로 우회한다.** (a) 법인을 세우고 API대행사를 신청한다(심사 반려 가능). (b) 고객이 이미 쓰는 사방넷·플레이오토 API를 거쳐 주문을 받는다. (c) 정산 데이터는 고객이 스마트스토어센터에서 엑셀로 내려받아 공유 폴더에 올린다(반자동). **스크래핑과 고객 ID·비밀번호 위임 로그인은 하지 않는다.**
2. **상품 범위는 "읽기 전용 + 알림"으로 시작한다.** 재고를 채널에 쓰는 기능은 기존 통합솔루션에 맡긴다.
3. **호스팅은 한국 리전에 고정 IP로 둔다.** 쿠팡·네이버·11번가가 모두 IP 화이트리스트를 요구한다. 서버리스나 GitHub Actions는 나가는 IP가 고정되지 않아 쓸 수 없다. 주문자 개인정보를 국외로 옮기는 문제도 함께 피할 수 있다.
4. **주문자 개인정보는 최소한만 수집하고 LLM에 보내지 않는다.** LLM에는 집계값만 넘긴다.

## 1. 채널별 연동 가능성

### 1-1. 요약표

| 채널 | 공식 API | 인증 방식 | 판매자 쪽 절차 | 대행사(제3자)가 운영해도 되나 | 제약 | 정산 데이터 |
|---|---|---|---|---|---|---|
| **네이버 스마트스토어** (커머스API) | 있음 | Client ID/Secret으로 전자서명해 OAuth2 토큰 발급 | 커머스API센터에서 애플리케이션 등록, 호출 IP 최대 3개 | **내스토어 앱 키를 받아 운영하는 것은 금지.** "커머스솔루션"(솔루션마켓 등록) 또는 "API대행사"(스마트스토어센터에서 대행사 지정)만 허용. API대행사는 **국내 법인 사업자** 요건 | API마다 초당 호출 허용량이 다르고 넘으면 429(GW.RATE_LIMIT). 애플리케이션 인증 기한이 지나면 자동 휴면 | 정산 API 있음(일별 정산, 건별 정산). 건별 조회는 기간을 하루 단위로만 넣을 수 있고, 혜택정산 금액은 0으로 나온다 |
| **쿠팡** (Wing Open API) | 있음 | Access Key/Secret Key로 HMAC 서명, 업체코드(vendorId) | WING에서 사업자 인증 후 키 발급(즉시 발급, 권한 반영에 최대 24시간). "연동업체 선택"(1개) 또는 "자체개발(직접입력)"에 IP 최대 10개 | **가능.** 자체개발 칸에 대행사 IP를 입력하는 방식을 연동 업체들이 공식 안내한다 | vendorId당 초당 5회를 넘으면 429. **키는 180일마다 만료되어 재발급이 필요하다.** IP·연동업체 목록은 한 달에 10회까지만 수정 가능 | 정산 API 있음(매출내역 조회 `revenue-history` 등) |
| **11번가** | 있음(셀러 API) | 헤더에 `openapikey` | 오픈API센터 서비스 등록, Seller API 정보에 IP 등록 | 가능. 셀러툴들이 판매자 키를 받아 쓰는 방식이 일반적이다 | XML 기반 구형 API | **정산 조회 API를 확인하지 못했다.** 셀러오피스 엑셀로 받는다고 가정 |
| **G마켓·옥션** (ESM Trading API) | 있음 | ESM+ 마스터 ID 기반 | ESM+에서 셀링툴 "사용함" 설정 후 셀링툴 업체 지정(상품·주문 각각 최대 5개) | **조건부.** 대행사가 셀링툴 업체로 등록돼야 하고, 업체 사업자 정보로 G마켓·옥션 판매자 회원 가입이 필수다. 승인은 "내부 지원 리소스 범위 안에서" 이루어지며 반려될 수 있다 | 승인 재량. 문의는 etapihelp@gmail.com | API 범위 확인 필요(엑셀 백업 경로 확보) |
| **카카오 선물하기** (카카오쇼핑 API) | 있음 | 마스터 계정으로 인증키를 만들고 승인 | 별도 접근 권한 신청 → 승인 | **조건부.** "연동대행사" 권한을 받은 뒤 대행사-판매자 연결 API로 매핑해야 한다 | 승인 재량. 사방넷 등은 이미 연동돼 있다 | 확인 못 함 → 엑셀 |
| **카페24** | 있음(REST, 품질 좋음) | OAuth 2.0(앱 등록, Redirect URI) | 개발자센터에 앱 등록, 판매자가 앱 설치·권한 동의 | 가능(앱 방식 자체가 제3자 연동용) | Leaky Bucket 방식(버킷이 1초에 2회씩 비워짐), 사용량 헤더 제공. 여러 쇼핑몰이 쓰는 비공개 앱에 앱스토어 심사가 필요한지는 **확인 필요** | 주문·결제 데이터로 계산(PG 정산은 별도) |
| **아임웹** | 있음(REST v2) | API Key/Secret으로 액세스 토큰 발급(OAuth 엔드포인트도 있음) | 관리자 > 외부 서비스 연동(API)에서 키 발급 | 가능 | 주문관리 v2 전환 때문에 `order_version` 파라미터 처리 필요 | 주문 데이터로 계산 |
| **고도몰** (NHN커머스) | 있음 | 제휴사키(파트너키) + 사용자키 | 개발자센터 등록("쇼핑몰직접개발" 또는 제휴사) 후 키 신청 | 조건부. 대행사가 여러 몰을 맡으려면 제휴사 등록이 필요해 보인다 | 키 발급 절차가 상대적으로 무겁다 | 주문 데이터로 계산 |

### 1-2. 스크래핑은 하지 않는다

- 판매자센터를 크롤링하려면 고객의 ID·비밀번호와 2단계 인증을 넘겨받아야 한다. 이렇게 하면 ① 플랫폼 약관상 계정 공유·자동 접속 금지에 걸리고 ② 계정이 정지되면 **고객 매출이 멈추며** 그 책임이 대행사로 온다 ③ 화면이 바뀔 때마다 깨진다. 1인 운영과 맞지 않는다.
- API가 없는 정산 데이터는 **"고객이 월 1회 또는 주 1회 엑셀을 공유 드라이브에 올리면 자동 파싱"**하는 반자동 방식으로 처리한다. 채널마다 엑셀 양식이 달라서 이 파싱이 오히려 AI가 쓸모 있는 지점이다(3절).

### 1-3. 통합솔루션 위에 얹는 방식 (사방넷·플레이오토)

| 솔루션 | API 조건(검색 기준) | 얻는 것 | 못 얻는 것 |
|---|---|---|---|
| 사방넷 | API 서비스 실버 **월 10만원**, API 2.0 스탠다드 월 27만원 / 프리미엄 월 48만원 (본 요금제와 별도) | 수십 개 채널의 주문 수집, 재고, 송장, 문의 데이터를 **커넥터 하나로** 받는다. 네이버·ESM·카카오 정책 문제를 솔루션사가 대신 해결한 상태 | 채널별 **수수료·정산 금액**은 기본적으로 들어오지 않는다고 봐야 한다(확인 필요) |
| 플레이오토 2.0 | BASIC 요금제 이상 + API연동 부가서비스 구매 + 개발자센터 신청(승인 2~5일) | 상품, 주문, 재고 API | 정산 |

**결론: "얹는" 방식이 이 사업의 기본 경로로 가장 현실적이다.**
- 타깃 고객(월매출 5천만~5억원, 다채널)은 이미 사방넷·플레이오토·이지어드민을 쓰고 있을 가능성이 높다. 이들의 불만은 "주문은 모였는데 **손익·정산 대사는 여전히 엑셀**"이다. 이 사업의 가치 제안과 정확히 겹친다.
- 구성: **주문·재고는 통합솔루션 API 1개, 정산은 쿠팡 API + 네이버(대행사 경로 또는 엑셀) + 기타 채널 엑셀.**
- 단점: 사방넷 API 월 10만원 이상을 고객이 추가로 낸다. 영업 메시지에서 "이미 내는 사방넷에 월 10만원만 더하면 엑셀 작업이 사라진다"로 정리해야 한다.
- 통합솔루션을 쓰지 않는 소형 셀러(스마트스토어 + 쿠팡 2채널)는 쿠팡 API + 네이버 엑셀로 시작하고, 법인 전환 뒤 네이버 API대행사로 바꾼다.

### 1-4. 네이버 문제의 선택지 비교

| 선택지 | 비용·시간 | 자동화 수준 | 위험 |
|---|---|---|---|
| A. 고객 내스토어 앱 키를 받아 대행사 서버에서 호출 | 0원 | 완전 자동 | **네이버 정책 위반**(공식 답변으로 명시). 적발 시 앱 휴면, 고객 신뢰 상실. **채택하지 않음** |
| B. 법인 설립 → API대행사 신청 | 법인 설립 실비 수십만원(셀프 등기 기준 추정) + 심사 기간 | 완전 자동, 판매자는 스마트스토어센터에서 대행사 지정만 하면 됨 | 신규·소규모 법인은 "실제 서비스로 판단하기 어렵다"는 이유로 반려될 수 있다. 첫 고객 3~5곳 레퍼런스를 만든 뒤 신청하는 것이 유리하다 |
| C. 통합솔루션 API 경유 | 고객이 월 10만원 이상 부담 | 주문은 자동, 정산은 엑셀 | 솔루션사 API 정책에 종속 |
| D. 엑셀 업로드 반자동 | 0원 | 반자동(고객이 주 1회 2분 작업) | 고객이 업로드를 잊는다 → 리마인드 알림으로 보완 |

**권장 순서: D와 C로 시작(1~3개월) → 고객 5곳 확보 후 법인 전환과 B 신청(3~6개월).** 법인 전환은 세금계산서와 B2B 신뢰 측면에서도 이득이 있어서, 이 사업을 계속한다면 어차피 할 일이다.

## 2. 재사용 아키텍처

### 2-1. 추천 스택: 코드 우선 (n8n은 보조로만)

| 항목 | 추천 | 이유 |
|---|---|---|
| 언어 | **Python 3.12** (pandas/polars로 대사·리포트, httpx로 커넥터) | 정산 대사와 손익 계산이 표 연산 중심이다. Claude Code가 생성·테스트하기도 쉽다. TypeScript도 가능하지만 데이터 처리량을 고려하면 Python이 낫다 |
| 실행 | **한국 리전 VPS 1대 + 고정 IP**(AWS Lightsail 서울 또는 Vultr 서울), Docker Compose, systemd timer/cron 또는 경량 작업 큐(APScheduler/RQ) | IP 화이트리스트(쿠팡 10개, 네이버 3개, 11번가) 때문에 고정 IP가 **필수**다. 예비 IP 1개를 처음부터 모든 고객 채널에 같이 등록해 둔다(쿠팡은 IP를 한 달에 10회까지만 수정 가능) |
| DB | **Postgres**: Supabase Pro(서울 리전) 또는 VPS 내 Postgres + 일일 백업 | 멀티테넌트 RLS, 대시보드, 백업 기능이 기본으로 들어 있다. Supabase Pro는 월 $25(컴퓨트 크레딧 $10 포함) |
| 비밀정보 | 고객 API 키는 **애플리케이션 레벨 봉투 암호화**(마스터 키는 환경변수나 KMS, DB에는 암호문만 저장). Supabase Vault도 가능 | 키가 유출되면 고객 채널 전체를 조작할 수 있다 |
| 출력 | 구글 시트(서비스 계정), Looker Studio, **슬랙/텔레그램(무료)**, 카카오 알림톡(솔라피, 건당 13원) | 알림톡은 카카오 비즈니스 채널과 템플릿 심사가 필요하다. 첫 고객은 슬랙/텔레그램/이메일로 시작한다 |
| 모니터링 | Healthchecks.io(크론 하트비트), Sentry(에러), Uptime Kuma | "조용한 실패"(작업이 아예 안 돈 경우)를 잡는 하트비트가 가장 중요하다 |
| n8n | **보조로만**(고객별 일회성 알림 흐름 등) | ① 쿠팡 HMAC, 네이버 전자서명, 페이지네이션, 429 재시도, 테스트를 노드로 짜면 유지보수가 더 어렵다 ② n8n Sustainable Use License는 "고객에게 n8n 자체에 대한 접근을 판매"하는 것을 막는다. 대행사 소유 인스턴스 하나에서 여러 고객 워크플로를 돌리는 형태는 해석 여지가 있다. 고객에게 n8n 화면을 주지 않으면 위험은 낮지만, 핵심을 코드로 짜면 이 논점이 아예 사라진다 |

### 2-2. 호스팅: 멀티테넌트 단일 코드베이스 (고객별 서버 분리 X)

- **코드 1벌, DB 1개, 모든 테이블에 `tenant_id`, Postgres RLS 적용.** 고객별 차이는 코드가 아니라 **설정(YAML/DB 레코드)**으로 표현한다. 예: 채널 목록, 수수료 규칙, 원가표, 리포트 수신자, 알림 임계값.
- 고객별 VPS 분리는 15곳이면 서버 15대를 패치·백업·모니터링해야 하고, IP도 15개를 관리해야 한다. 1인에게 맞지 않는다.
- 예외: 고객이 "우리 데이터는 우리 계정에"를 요구하면 같은 Docker 이미지를 고객의 클라우드 계정에 배포하는 상위 요금제로 판다.
- 고객 해지 시: 데이터 내보내기(CSV/시트)와 삭제 절차를 계약서에 넣는다.

## 3. AI가 들어가는 지점과 비용

**솔직한 평가: 이 사업의 본체는 결정론적 데이터 파이프라인(ETL + 규칙)이고, LLM은 보조다.** 가장 큰 AI 레버리지는 고객에게 납품하는 기능이 아니라 **창업자가 Claude Code로 커넥터·테스트를 빠르게 만드는 개발 생산성**이다. 영업에서 "AI 자동화"를 앞세우되, 정산 숫자 자체는 절대 LLM이 계산하지 않게 설계한다(환각 차단).

모델 가격(2026-10 공식): Claude Haiku 4.5 입력 $1 / 출력 $5 per MTok(배치 $0.5/$2.5), Claude Sonnet 5.5 입력 $2 / 출력 $10(배치 $1/$5). Claude 4.7 이후 모델은 같은 텍스트에 토큰이 약 30% 더 나오므로 아래 계산에 1.3배 버퍼를 둔다.

| # | 지점 | 방식 | 고객 1곳 월 사용량 가정 | 계산식 | 월 비용 |
|---|---|---|---|---|---|
| 1 | 상품명·옵션 매칭(채널 상품 ↔ 내부 SKU) | 문자열 정규화 → 후보 추출 → Haiku가 매칭·신뢰도 판정 → 사람 승인. **셋업 시간을 가장 많이 줄인다** | 셋업 1회 500개, 이후 신규 월 50개. 건당 입력 300, 출력 100토큰(배치) | 셋업: 500×(300×0.5+100×2.5)/1M = $0.20 (1회). 월: 50건 → $0.02 | $0.02 |
| 2 | 정산 엑셀 양식 파싱(컬럼 매핑) | 새 양식이 들어오면 Sonnet이 컬럼 매핑을 제안 → 코드 파서로 고정. 매월 실행하는 것이 아니라 양식이 바뀔 때만 | 월 1회 10k 입력 / 2k 출력 | 10k×2/1M + 2k×10/1M = $0.04 | $0.04 |
| 3 | 정산 이상 탐지 | **탐지는 규칙**(예상 수수료율 대비 편차, 미정산, 중복 차감, 반품비 이상)과 통계(z-score)로 한다. **LLM은 탐지 결과를 사장님 말투로 설명하고 조치 안내만** | 주 1회 20k 입력 / 2k 출력 | 4×(20k×2+2k×10)/1M = $0.24 | $0.24 |
| 4 | 일일 매출·마진 자연어 요약 | 집계표(개인정보 없음)를 받아 3~5줄 요약 + 특이사항 | 일 6k 입력 / 0.6k 출력 × 30일 | 30×(6k×2+0.6k×10)/1M = $0.54 | $0.54 |
| 5 | 월간 손익 리포트 해설 | 채널·상품별 손익표 → 해설과 다음 달 액션 3개 | 월 50k 입력 / 4k 출력 | 50k×2/1M + 4k×10/1M = $0.14 | $0.14 |
| 6 | (선택, 상위 요금제) 대화형 질의 "지난주 쿠팡 마진 얼마?" | 큐레이션된 뷰에 대한 text-to-SQL + 결과 검증, 읽기 전용 DB 롤 | 월 100문 × 8k 입력 / 0.5k 출력 | 100×(8k×2+0.5k×10)/1M = $2.10 | (옵션) $2.10 |
| | **기본 합계** | | | $0.98 × 1.3(토크나이저·재시도 버퍼) | **약 $1.3 (≈ 1,800원)** |

- LLM 비용은 고객당 월 2천원 안팎(대화형 옵션을 넣어도 5천원 이하)으로 **사업성에 영향이 없다.**
- **개인정보 원칙**: LLM 입력에는 주문자 이름·연락처·주소를 절대 넣지 않는다. Claude API는 기본이 글로벌 처리라서, 개인정보를 넣으면 개인정보보호법 제28조의8 국외 이전 문제가 생긴다. 집계값과 상품명만 보낸다.

## 5. 운영 리스크와 1인 15곳 감당 가능성

### 5-1. 리스크별 대응

| 리스크 | 발생 빈도·영향 | 대응 |
|---|---|---|
| **쿠팡 키 180일 만료** | 15곳이면 **매달 약 2.5건** 재발급이 필요하다. 고객이 직접 해야 하는 일이다 | DB에 만료일 저장, D-30/D-7/D-1에 고객과 창업자에게 자동 알림. 재발급 안내 문서와 2분 영상 |

| API 스펙 변경(필드 추가·폐기, 버전 종료) | 채널당 연 1~3회 | 원본 JSON(raw_events) 보관 → 파서만 고쳐서 재처리. 네이버·쿠팡 개발자 공지와 GitHub Discussions를 RSS/메일로 구독. 계약 테스트(실제 응답 스냅샷)를 CI에 둔다 |
| API 장애·429 | 주 단위로 발생 | 지수 백오프, 커서 기반 재수집으로 멱등성 확보. 리포트에 "데이터 지연" 표시 |
| 조용한 실패(크론이 안 돈 경우) | 가장 위험(고객이 먼저 발견하면 신뢰 상실) | 작업마다 Healthchecks 하트비트, 일일 "수집 건수 0" 이상 감지 |
| 정산 엑셀 양식 변경 | 분기 1회 수준 | 파서가 실패하면 즉시 알림 → LLM이 컬럼 매핑 제안 → 사람 확인 |
| **고객 API 키 유출** | 낮은 확률, 치명적 영향 | 봉투 암호화, 서버 SSH 키 전용 로그인, DB 접근 IP 제한, 키는 로그에 남기지 않음, 쓰기 권한이 필요 없는 채널은 읽기 범위만 요청 |
| **주문자 개인정보** | 법적 의무 발생 | ① **수집 최소화**: 손익·대사에는 이름·주소·연락처가 필요 없다. 수집하더라도 즉시 마스킹·해시 ② 보관기간 90일 후 파기 ③ 고객과 **개인정보 처리위탁 계약** 체결(고객의 개인정보처리방침에 수탁자로 기재) ④ 안전성 확보조치: 접근권한 관리, 암호화, 접속기록 보관 ⑤ 한국 리전 저장, LLM에는 개인정보 미전송 → 국외 이전 이슈 회피 |
| 백업 | | 일일 pg_dump 암호화본을 다른 사업자의 오브젝트 스토리지에 30일 보관 + 분기 1회 복구 리허설. 원본 데이터는 채널에서 재수집할 수 있어서 백업 실패의 피해는 제한적이다(원가표·SKU 매핑·설정이 진짜 자산) |
| 단일 서버·단일 IP 장애 | 연 수 회 | 예비 IP를 미리 등록, IaC(Docker Compose + 설정 저장소)로 1시간 안에 재구축 |
| 플랫폼 정책 변경(쿠팡 연동 정책, 네이버 대행사 요건 강화) | 사업 존속에 영향 | 통합솔루션 경유와 엑셀 경로를 항상 백업 경로로 유지 |
| 오버셀 책임 | 재고 쓰기 기능을 넣으면 발생 | 초기에는 쓰기 기능을 팔지 않는다. 나중에 넣는다면 계약서에 책임 한도를 둔다 |
| 범용화 | 사방넷·플레이오토·이지어드민, 그랜터·클로브 같은 SaaS가 손익 대시보드를 강화 중 | 6절 |

### 5-2. 1인 15곳: 조건부 가능

주당 시간 계산:

| 항목 | 주당 시간 |
|---|---|
| 정기 운영(리포트 검수, 이상 건 확인, 고객 문의) 15곳 × 0.5~0.8h | 7.5~12h |
| 장애·API 변경 대응(평균) | 3~5h |
| 키 만료·온보딩 지원 | 1~2h |
| 월 1건 소규모 개선 × 15곳 = 월 15건 × 2~3h ÷ 4.3주 | 7~10h |
| **운영 소계** | **18.5~29h** |
| 신규 셋업 월 2건 × 6~12h ÷ 4.3주 | 3~6h |
| 영업·진단 콜·콘텐츠 | 5~8h |
| **총계** | **26.5~43h** |

- 창업자의 주 30시간 이상과 비교하면 **상단 시나리오에서는 넘친다.** 가장 큰 변수는 "월 1건 소규모 개선" 약속이다. 15곳이면 매주 3~4건의 개발 요청이 쌓인다.
- **15곳을 감당하는 조건**: ① 지원 채널과 리포트를 표준 메뉴로 고정하고 커스텀을 줄인다 ② "월 1건 개선"을 "분기 1건" 또는 상위 요금제 전용으로 바꾼다 ③ 하트비트·만료 알림·자동 재처리로 장애 대응을 주 3시간 이하로 낮춘다 ④ 고객 문의 창구를 단일 채널(슬랙 커넥트 또는 카톡 채널)로 묶는다.
- 위 장치가 없으면 **현실적 상한은 8~10곳**이다. 1~3개월 차에는 8곳을 목표로 잡고, 운영 지표(주당 장애 시간, 고객당 문의 수)를 본 뒤 늘린다.

## 6. 기술적 해자: 약함~보통

| 요소 | 강도 | 설명 |
|---|---|---|
| 기술 자체 | 약함 | API 연동과 대사 로직은 크몽 판매자도 만든다. Claude Code가 이 장벽을 더 낮춘다 |
| 고객별 원가표·SKU 매핑·수수료 예외 규칙 | **보통** | 셋업 때 고객과 같이 만든 데이터라서 옮기려면 다시 정리해야 한다. 실질적인 전환 비용 |
| 매일 받는 결과물(일일 리포트·알림)에 대한 습관 | 보통 | 해지하면 내일 아침 리포트가 끊긴다. `02-screening.md`가 제안한 "결과물로 파는 운영비"와 같은 방향 |
| 채널 정책 자격(네이버 API대행사, ESM 셀링툴, 카카오 연동대행사) | 보통(확보 시) | 법인과 심사가 필요해서 크몽 개인 판매자는 따라오기 어렵다. **확보하면 이게 가장 확실한 진입장벽이다** |
| 정산 규칙 라이브러리와 회귀 테스트 | 약함~보통 | 고객이 늘수록 예외 처리가 쌓인다. 외부에서는 보이지 않는 품질 차이 |
| 범용화 위험 | 높음 | 통합솔루션이 "손익 리포트"를 기본 기능으로 넣으면 단순 리포트 상품은 사라진다. 대응: 표준 SaaS가 못 하는 **고객별 예외 처리와 사람이 검수하는 월간 손익 해설**로 위치를 잡는다 |

## 7. 2주 실험(실험 A)에 반영할 수정사항

1. **데모는 "쿠팡 API + 스마트스토어 정산 엑셀 업로드"로 만든다.** 네이버 내스토어 키를 받아 데모하는 방식은 정책 위반이라 쓰지 않는다.
2. 진단 콜에서 반드시 물어볼 것: ① 통합솔루션 사용 여부와 요금제(사방넷·플레이오토 API를 쓸 수 있는가) ② 채널 목록(표준 채널 밖이면 추가 견적) ③ 원가표 존재 여부(없으면 셋업 시간 2배).
3. 크몽 29만원 라이트 상품은 "1회성 스크립트 납품"이 아니라 **창업자 서버에서 돌아가는 1개월 체험 + 이후 월 운영 전환**으로 설계한다(크몽 정책 안에서).
4. 서버는 1일차에 서울 리전 VPS와 고정 IP를 잡고, 쿠팡 테스트 키로 IP 등록 흐름까지 검증한다.
5. 법인 전환과 네이버 API대행사 신청은 **유료 고객 3곳 확보 시점**에 결정한다.
