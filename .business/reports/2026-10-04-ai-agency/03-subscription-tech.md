## 2. 납품 속도를 높이는 표준 스택과 템플릿 키트

### 2-1. 판단 규칙: 노코드 워크플로 vs 코드

| 상황 | 선택 | 이유 |
|---|---|---|
| SaaS 간 단방향 연결, 단계 10개 이하, 고객 담당자가 나중에 직접 고칠 수도 있음 | **워크플로 툴**(고객 소유 n8n Cloud, 또는 Activepieces) | 화면으로 보이니 인수인계가 쉽고, 고객이 "블랙박스"라 느끼지 않음 |
| 돈·개인정보가 오가는 처리, 멱등성·재시도·테스트가 필요, 데이터 변환 로직이 복잡 | **코드**(TypeScript, Supabase Edge Functions 또는 Vercel Functions + 크론) | 테스트·버전관리·리뷰가 가능하다. Claude Code가 가장 빠르게 만드는 형태 |
| 사람이 보는 화면(어드민·대시보드) | **Next.js + Supabase 키트**(기본), 고객이 이미 Retool을 쓰면 Retool | 키트를 재사용하면 6~10h 안에 가능 |
| LLM 처리 | **Anthropic API 직접 호출**(Haiku 4.5: 분류·추출, Sonnet 5.5: 요약·초안·RAG 답변) + 구조화 출력 | 범용 API로 충분하다. 파인튜닝·자체 모델은 필요 없음 |

> 이 사업에 자체 모델이나 파인튜닝은 필요 없다. 15개 유형 전부 범용 LLM API + 연동 코드로 해결된다. 그 말은 곧 **기술로는 차별화할 수 없다**는 뜻이기도 하다(6절).

## 3. 고객 환경 접근, 보안, 코드 소유권·인수인계

### 3-1. 어디서 돌릴 것인가: "고객 소유, 창업자 운영"을 기본으로

| 방식 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **A. 고객 계정에서 작업**(고객 GitHub org·Vercel 팀·Supabase org·n8n Cloud에 창업자를 멤버로 초대, 결제는 고객) | 소유권이 명확하다. 해지 시 인수인계 비용이 0에 가깝다. 장애 책임 경계가 분명하다. n8n 라이선스 문제가 없다 | 계정 초대·권한 대기로 시작이 늦어진다. 전환비용(락인)이 낮다 | **기본값** |
| **B. 창업자 인프라에서 호스팅** | 시작이 빠르다. 락인이 생긴다(스크리닝 문서의 의도) | **n8n은 여러 고객의 워크플로·자격증명을 창업자 인스턴스에서 호스팅하면 상용 라이선스 대상.** 개인정보 수탁 책임이 창업자에게 집중된다. 장애가 나면 전부 창업자 책임 | 코드 기반 또는 **Activepieces(MIT)**로만, 인프라가 없는 작은 고객에 한해 허용 |
| C. 하이브리드 | — | — | 실무 권장: 인프라 있는 고객은 A, 없는 고객은 B(코드/Activepieces) + "해지 시 이전 패키지 1주 내 제공"을 계약에 명시 |

**락인을 인프라로 만들지 말고 운영으로 만든다.** 해지 방지 장치는 "호스팅 볼모"가 아니라 "모니터링·고장 수리·주간 상태 리포트가 구독에 포함돼 있고, 해지하면 그게 멈춘다"여야 한다. 스타트업 고객은 실사·보안 질문지에서 "외부 개인 개발자 서버에 고객 데이터가 있다"는 것을 문제 삼는다(추정).

### 3-2. 보안 수칙

1. **비밀번호를 받지 않는다.** 고객이 OAuth로 직접 연결하거나, 고객이 발급한 **최소 권한 서비스 계정·API 키**만 쓴다. 키는 고객 계정 환경변수에만 둔다. 메신저·메일로 키를 받지 않는다(받아야 하면 비밀번호 금고 공유 링크로).
2. **Claude Code 안전 설정**: 프로젝트 설정에서 `.env*`, 자격증명 파일 읽기를 거부(deny)한다. 실데이터 대신 마스킹 샘플로 개발한다. 운영 DB에는 읽기 전용 계정으로 붙는다.
3. **고객마다 분리**: 레포·Supabase 프로젝트·비밀번호 금고 컬렉션을 고객별로 나눈다. 한 고객 키가 다른 고객 작업공간에 들어가지 않게 한다.
4. **쓰기 작업 안전장치**: 결제·정산·대량 발송·DB 일괄 수정은 dry-run 모드 + 사람 승인 단계를 기본으로 넣는다.
5. **접근 회수**: 해지·건 종료 시 창업자 계정 권한 회수 체크리스트를 인수인계 문서에 포함한다.

### 3-3. 개인정보

- 고객사 고객의 개인정보를 다루는 순간 창업자는 개인정보보호법상 **수탁자**가 된다. 제26조에 따라 **문서(위탁 계약)**가 필요하다(목적 외 처리 금지, 기술적·관리적 보호조치 포함). 구독 계약서에 처리위탁 조항이나 별첨을 표준으로 넣는다.
- **LLM API로 개인정보를 보내는 것은 재위탁과 국외 이전에 해당할 수 있다.** 수탁자가 다시 위탁하려면 위탁자 동의가 필요하다. → 계약서에 "LLM 공급자(Anthropic 등) 사용"을 명시해 동의를 받고, 고객사 개인정보처리방침의 수탁자·국외이전 항목 갱신을 안내한다. 가능하면 LLM에 보내기 전에 이름·연락처를 마스킹한다.
- 주민번호·건강정보·금융정보가 들어가는 요청은 구독 범위 밖으로 둔다(거절 또는 별도 계약).

### 3-4. 코드 소유권·인수인계

| 항목 | 표준 조건(권장) |
|---|---|
| 납품물 저작권 | 해당 월 구독료를 완납하면 고객에게 귀속 |
| 템플릿 키트(K1~K9) | **창업자 보유.** 고객에게는 비독점·영구 사용권을 준다. 이 조항이 없으면 키트를 다음 고객에게 재사용할 근거가 흔들린다 |
| 저장 위치 | 처음부터 고객 GitHub org(방식 A). 방식 B는 해지 시 레포 이전 |
| 건별 인수인계 | README(무엇을, 언제, 어디서 도는지), 런북(고장 시 확인 순서), 환경변수 목록(값 제외), 화면 녹화 설명 영상 2~3분 |
| 해지 시 | 이전 패키지(레포 이전, 워크플로 export, 자격증명 교체 안내) 1주 내 제공. 이후 지원은 시간당 또는 유지 플랜 |

## 4. 1인 월 처리 용량과 월 비용

### 4-1. 시간 예산

- 주 30시간 = 납품 20~22시간 + 영업·관리 8~10시간 (`02-ideas.md` 공통 가정과 같음)
- 스탠다드 고객 1곳의 주간 부하 (추정)

| 항목 | 가벼운 고객 | 보통 고객 | 최대 사용 고객 |
|---|---|---|---|
| 주간 요청 수 | 0.8건 | 1.2건 | 1.7건(동시 1건, 72h 회전의 물리적 상한) |
| 요청 처리(× 5.5h) | 4.4h | 6.6h | 9.4h |
| 커뮤니케이션·요구 정리 | 1h | 1h | 1.5h |
| 유지보수(누적 자동화 고장 수리) | 0.5h → 6개월 차 1.5h | 0.5h → 2h | 1h → 2.5h |
| **합계** | **약 6~7h** | **약 8~10h** | **약 12~13h** |

**고객 수별 주당 시간**

| 고객 수(스탠다드) | 보통 고객만 | 섞였을 때(가벼움 2 + 보통 1 + 최대 1) | 판정 |
|---|---|---|---|
| 3곳 | 24~30h | — | 안정(약간 초과 시 영업 시간을 줄여 흡수) |
| 4곳 | 32~40h | 약 33~39h | 평균 사용률이 낮을 때만 가능. 그 외에는 납기 지연 |
| 5곳 | 40~50h | — | **불가.** 주 30h를 넘고 72h 납기가 깨진다 |

→ **1인 상한: 스탠다드 3곳(안정) ~ 4곳(최대).** 4번째 자리는 라이트(99만원, 월 2건, 5영업일) 고객 1~2곳으로 채우는 쪽이 안전하다. 예) 199만 × 3 + 99만 × 1 = **696만원**, 주 약 30h.

- 시간당 실수령 환산: 199만원 ÷ (9h × 4.3주) ≈ **5.1만원/h**. Kill 기준인 1건 12시간이 현실이 되면 같은 계산이 약 2.7만원/h로 떨어지고 상한은 2곳이 된다. 실험 B의 12시간 기준은 타당하다.
- **납기 문구는 "평균 48~72시간, 보장은 5영업일"로 쓴다.** 고객 3곳이 동시에 요청하면 72h 안에 18h를 해야 하는데, 이것은 가능하다. 그러나 4곳이 동시에 요청하면 22h+ 라 영업·유지보수와 겹칠 때 깨진다. 9DOGS도 "평균 5영업일"로 표기한다.

### 4-3. 납품물의 LLM 운영 비용 계산 (고객 1곳, 월)

계산식: 월 비용 = 건수 × (입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가) / 1,000,000

| 납품물 | 모델 | 가정 | 계산 | 월 비용 |
|---|---|---|---|---|
| 사내 RAG 슬랙봇 | Sonnet 5.5 ($2/$10) | 월 500질문, 입력 6,000(문서 맥락) / 출력 500 | 500 × (6,000×2 + 500×10)/1M = 500 × $0.017 | **$8.5 (약 1.2만원)** |
| 계약서 요약·조항 추출 | Sonnet 5.5 | 월 200건, 입력 20,000 / 출력 1,500 | 200 × (0.04 + 0.015) | **$11 (약 1.5만원)** |
| 문의 분류 | Haiku 4.5 ($1/$5) | 월 3,000건, 입력 1,500 / 출력 200 | 3,000 × (0.0015 + 0.001) | **$7.5 (약 1.1만원)** |
| 리드 보강 정규화 | Haiku 4.5 | 월 1,000건, 입력 3,000 / 출력 300 | 1,000 × (0.003 + 0.0015) | **$4.5 (약 0.6만원)** |

→ 전부 켜도 **고객 1곳당 월 $30 안팎(약 4만원)**. 프롬프트 캐싱(캐시 입력 최대 90% 할인)과 Batch(50% 할인)를 쓰면 더 낮아진다. LLM 비용은 이 사업의 수지를 좌우하지 않는다. **원가는 창업자의 시간이다.**

## 5. 기술·운영 리스크

| 리스크 | 심각도 | 내용 | 대응 |
|---|---|---|---|
| **범위 확장** | 상 | "이것도 같이"가 쌓여 1건이 20h가 된다. 구독형은 고객이 추가 요청을 공짜로 느낀다 | ① 1건 = 실작업 8h 이내 + 수정 1회 ② 접수 폼 필수 항목이 다 채워져야 SLA 시계 시작 ③ 8h를 넘으면 창업자가 분할안을 제시(고객 승인) ④ 14·15번 유형은 "구독 범위 밖"으로 명시 |
| **유지보수 부채 누적** | 상 | 자동화는 고장 난다: OAuth 토큰 만료, 고객이 시트 열 이름을 바꿈, 외부 API 변경, 요청 한도(rate limit). 6개월이면 고객 1곳에 활성 자동화 20~30개가 쌓이고, 월 고장률을 개당 5~10%로 잡으면 **월 1~3건 수리**가 생긴다(추정). 시간 예산 4-1의 유지보수 항목이 계속 커진다 | ① **고장 수리는 요청 슬롯과 별도, 영업일 1일 내 착수**를 구독 가치로 판다 ② 모든 납품물에 K8 하트비트·에러 알림 의무화(고객보다 먼저 안다) ③ 구독당 "모니터링 대상 활성 자동화 N개(예: 25개)" 상한, 넘으면 오래된 것 정리 또는 상위 플랜 ④ **해지 후 고장은 무상 수리하지 않음.** 유지 전용 플랜(월 29만원, 수리만, 신규 개발 없음)을 둔다. 이게 해지 고객의 다운그레이드 경로가 된다 |
| **고객사 시스템 장애 책임** | 상 | 결제 웹훅 중복 처리, 대량 알림 오발송, DB 일괄 수정 실수는 고객 매출·평판 손해로 이어진다 | ① 계약서에 **손해배상 상한 = 직전 3개월 구독료**, 간접손해·고객 시스템·외부 SaaS 장애 면책 ② 돈·대량 발송·DB 쓰기 작업은 dry-run + 승인 단계 + 멱등키 기본 ③ 운영 DB는 읽기 전용 계정, 쓰기는 별도 테이블·스테이징 먼저 ④ 개인 배상책임보험(전문직·IT 배상) 가입 검토 |
| **n8n 라이선스** | 중 | 창업자 인스턴스에서 여러 고객 워크플로·자격증명을 호스팅하면 상용 라이선스 대상 | 방식 A(고객 소유) 기본. 창업자 호스팅은 코드 또는 Activepieces(MIT) |
| **접근권한 대기로 SLA 위반** | 중 | 스타트업은 권한 부여를 미루고, 그 시간도 "납기 지연"으로 인식된다 | 온보딩 1회차에 공통 권한(GitHub·Vercel·Supabase·슬랙 봇·노션 통합)을 일괄 확보. 시계는 권한 확보 후 시작 |
| **환각·정확도** | 중 | 9·10·12번 유형의 LLM 출력 오류 | 출처 링크 표시, 사람 승인 단계, 샘플 20건 정확도 확인 후 납품, "법률·세무 판단 아님" 문구 |
| **Claude Code 한도·장애** | 중 | Max 20x에도 주간 한도가 있고, 마감 직전 한도에 걸리면 납기가 깨진다 | 마감 집중을 피하는 스케줄링, 비상용 API 키(종량제)로 대체 실행 경로 확보 |
| **API 공급자 종속** | 하 | 납품물 LLM 호출이 한 공급자에 묶임 | K4 래퍼로 모델 교체 가능하게. 납품물 비용 비중이 작아 영향 작음 |
| **범용화(가장 큰 장기 리스크)** | 상 | Claude Code·n8n AI 워크플로 빌더·노션/Zapier 에이전트로 1·2·4번 같은 단순 자동화는 스타트업 직원이 직접 만든다. 6~12개월 안에 "자동화를 만들어 주는 것"의 가치가 떨어진다(추정) | 판매 단위를 "자동화 개수"에서 **"운영 책임(고장 나도 누가 고치나)"**과 **"백로그를 대신 생각해 주는 것"**으로 옮긴다. 4-1 기준으로 고객 내부 개발 인력이 생기면 이탈한다는 점을 전제로 고객 선정 |

## 6. 기술적 해자

| 요소 | 있나 | 평가 |
|---|---|---|
| 독자 데이터 | 없음 | 고객 데이터는 고객 것이다. 모을 수도 없고, 모아서도 안 된다 |
| 독자 모델·기술 | 없음 | 범용 API + 연동 코드. 누구나 같은 스택을 쓴다 |
| 템플릿 키트 | 약함 | 납기·원가 우위는 되지만 3~6개월이면 경쟁자도 만든다 |
| 워크플로 통합 | 중간 | 고객별 CLAUDE.md·런북·자동화 지도가 쌓일수록 다른 공급자로 옮기는 비용이 생긴다. **유일하게 시간이 갈수록 커지는 해자** |
| 운영·평가 체계 | 중간 | 하트비트·주간 상태 리포트·고장 대응 기록. 경쟁 프리랜서 대부분이 하지 않는다 |
| 관계·신뢰 | 중간 | 1인 상한 3~4곳이라 관계가 곧 사업이다. 반대로 1곳 이탈 = 매출 25~33% |

→ **기술 해자는 없다고 보는 게 맞다.** 방어력은 "고객별 운영 맥락 + 유지보수 책임"에서 나온다. 그래서 3절의 "인프라 락인 대신 운영 락인"이 해자 전략과 같은 이야기다.

## 7. MVP(납품 체계)까지의 일정

| 기간 | 할 일 | 산출물 |
|---|---|---|
| 1주차 (10/6~10/12, 약 30h) | 실험 B 랜딩·지인 연락과 병행. 데모 3종 제작하면서 K1~K4·K8·K9 추출 | 데모 3종, 키트 v0, 접수 폼, 계약서 초안(처리위탁·IP·책임제한 조항) |
| 2주차 (10/13~10/19) | 데모 고객 3곳 실제 납품, **건별 실작업 시간 기록**, K5~K7 보강 | 데모 시간 기록표(Kill 판정 자료), 키트 v1 |
| 3~4주차 | 유료 1~2곳 온보딩, 권한 일괄 확보 체크리스트 정착 | 운영 런북 템플릿, 주간 상태 리포트 자동화 |

- 인력: 창업자 1인으로 충분하다. 외주는 필요 없다.
- 노코드·로우코드로 가능한 부분: 1·2·4·12·13번 유형(워크플로 툴), 5번(기성 BI), 8번 일부(Retool/Appsmith), 요청 접수·백로그(노션/Tally).

## 8. 판정 근거 정리

**조건부 가능.** 조건 4개.
1. **범위**: 1건 = 실작업 8시간 이내. 시계는 접근권한·샘플 확보 후 시작. 14·15번 유형은 구독 범위 밖.
2. **인프라**: 고객 소유 환경 기본(n8n 라이선스와 개인정보 수탁 리스크 회피). 창업자 호스팅은 코드나 Activepieces로만.
3. **용량**: 스탠다드 3곳 + 라이트 1곳이 상한. 납기 문구는 "평균 48~72시간, 보장 5영업일".
4. **계약**: 처리위탁 조항(LLM 재위탁 동의 포함), 키트 IP 창업자 보유, 손해배상 상한, 해지 후 유지 전용 플랜.

이 4개를 지키면 기술 면에서 막히는 지점은 없다. 실험 B에서 진짜로 봐야 할 숫자는 **"데모 건당 실작업 시간(목표 6시간 이하, Kill 12시간)"**과 **"고객 백로그 깊이"**다.
